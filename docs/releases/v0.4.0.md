## 0. About this release

v0.4.0 is Fincas's first public release. The tested upgrade path is the Pin
lineage: a downstream deployment that adopted Fincas as a package through
`docs/pin/cutover-runbook.md`, and the release candidates before it
(`v0.3.0-rc.1`, `v0.4.0-rc.1`, `v0.4.0-rc.7` are the upgrade paths CI
replays). Fixes after the tag land on `main` and ship as v0.4.1, v0.4.2, ...;
the public release is always the latest v0.4.x
(`docs/release-hardening-plan.md`, section 0).

**Tags.** On the dev repo, `v0.4.0` is commit `3f5a4ff` (tagged 2026-10-27),
the same tree as `v0.4.0-rc.8`: the nightly on that tree was green (journeys
R0 to R10 from a fresh seed, nine themes with 0 findings) and the downstream
smoked it on its rehearsal host the same day (image built from the SHA,
`migrate` applied `products.0005` and the variant view on a prod-restore
copy, schema parity 0 unexpected, every consistency check clean, 160 staff
page loads with 0 tracebacks). The public repository's `v0.4.0` points at the
squashed release commit (`docs/release-process.md`, section 3.7); its SHA is
recorded here when it is pushed.

One instance per company: Fincas runs one Company per deployment by design
(section 3).

**The product is now called Fincas** (renamed from Golden ERP before this
release). What changed: the distribution name (`pip install fincas`; a
downstream requirement line reads `fincas @ git+ssh://…`, and pip refuses the
old `golden-erp @` name against the new metadata), the UI, email and admin
branding, the OpenAPI title and the webhook `User-Agent`
(`Fincas-Webhooks/1.0`). What did not change, on purpose: the Python package
`golden_erp`, every `GOLDEN_*` setting and environment variable, the
`X-Golden-*` webhook headers and the `X-Golden-Email-Log` mail header, the
`golden_erp.plugins` entry-point group, the JWT issuer `golden-erp`, and the
values stored in rows (`provider="golden"`). A downstream upgrade touches only
its requirement line.

## 1. Before you upgrade

A downstream on the Pin path follows `docs/pin/cutover-runbook.md` (§2
pre-flight through §12 rollback); the steps below are the Fincas-side part
of any upgrade, in order, with what each one prints when it is right. The
7.1 dry-run timings go in the table of section 4.

1. **Set the required secrets** (list below). Production settings turn on
   `core.E060`, and `migrate` refuses until every one is set:

   ```bash
   python manage.py generate_secrets          # prints a fresh set, one NAME=value per line
   # put them in the environment: Fly secrets, the compose .env, a systemd
   # EnvironmentFile, a Kubernetes Secret, ...
   ```

   Expected when one is missing:
   `SystemCheckError: (core.E060) Production secrets are not set: API_JWT_SIGNING_KEY (signs API bearer tokens), ...`

2. **Settings:** `GOLDEN_PORTAL_COMPANY=<company uuid>` whenever the
   database holds more than one `Company` (a fresh install with one needs
   nothing). Without it every portal login is 503 `portal_not_configured`
   and `parties.E001` fails every management command, `migrate` included.
   More than one Company is not supported (section 3): the planned
   `core.E070` refuses `migrate` with
   `N companies exist. Fincas runs one company per instance; keep one Company and run a separate instance for another company.`

3. **Back up, then migrate** (`migrate --plan` first on a copy):

   ```bash
   python manage.py migrate --plan            # expected: the migrations of section 4, nothing else
   python manage.py migrate --noinput         # expected: "Applying <app>.<migration>... OK" for each; no E060, no parties.E001
   ```

4. **Reconcile** (idempotent; `--fix` writes, `--check` must then exit 0):

   ```bash
   python manage.py reconcile_engagements --fix && python manage.py reconcile_engagements --check
   # expected last line: "drift: 0 engagement(s)"
   python manage.py reconcile_parties --fix && python manage.py reconcile_parties --check
   # expected: no "drift issue(s)"; conflicts and pending facts are listed, not failures
   ```

5. **Smoke** (runbook §11; exit codes in `docs/deployment.md` §9):

   ```bash
   python manage.py smoke_cutover || rc=$?
   # expected, one line per check:
   #   companies: observed=1 threshold=1 -> OK (runbook §7; plan 7.1: one Company per instance)
   #   migrations: observed=0 unapplied threshold=0 unapplied -> OK (...)
   #   staff_login: observed=N staff principal(s), M superuser(s) threshold=>=1 -> OK (...)
   #   storefront_identity: observed=present, 7/7 permissions, pinned=none (by design) threshold=... -> OK (...)
   #   outbox_dead: observed=0 threshold=<=0 -> OK (...)
   #   outbox_overdue: observed=no due rows threshold=<=30 min -> OK (...)
   #   engagements_drift: observed=0 threshold=0 -> OK (...)
   #   parties_drift: observed=0 drift threshold=0 drift -> OK (...)
   #   <manual rows: quote -> order -> PDF, storefront pages, portal login, stock, schema parity>
   #   smoke_cutover: OK. Run the manual rows above, then go (runbook §11).
   # rc unset: OK. rc=10: DEGRADED, act on each DEGRADED line. rc=20: ROLL BACK, runbook §12.
   ```

## 2. Behavior changes staff will notice

_What a person sees on a screen, from `v0.4.0-rc.4` to the tag. The PR
number is where the detail lives. A deployment that keeps its own theme and
brand (the downstream does) sees none of the first item._

**Name and look**

- **The product is called Fincas** (#170): page titles, the sign-in shell,
  emails, the Django admin header and the API docs say Fincas. The default
  theme is the new light `fincas` theme (violet accent, Manrope); the theme
  picker still lists every earlier theme, and a deployment pins its own with
  `ERP_DEFAULT_THEME`.
- **US English everywhere** (#128): color, canceled, organization, inquiry,
  and the status labels that went with them (quantity shipped, sub-order
  labeled, picked, shipped). Stored values are unchanged; only the labels.
- **Styled 403, 404 and 500 pages** on the sign-in shell, each with a
  sign-out form and a back link (#131). A non-staff login on `/erp/` gets
  the styled 403, not a blank one.
- **Keyboard and screen readers** (#153): scrolling tables are focusable
  regions, every button and nav link keeps a visible focus ring, the active
  page number follows the theme, printed documents carry a language and
  title.

**Quotes and orders**

- **Several people on a quote or order** (#128): a People card on the
  editor; the customer's own person and the people related to the customer
  are candidates; the list carries through convert, duplicate and revision.
- **Lines move between shipments and reorder** (#128): drag a line to
  another shipment group or use the per-line move control; the order is
  saved. Locked lines stay pinned and can no longer be deleted.
- **Enter in a search field picks the suggestion, never submits the form**
  (F-088, #155).
- **One click, one record** (F-033, #134): convert, record payment and send
  disable while the request is pending, and the server refuses a duplicate.
- **Money reads `$1,234.56`** for USD; other currencies keep their code.
  Invoice links open in a new tab; the quote list links its engagement
  (#128).

**CRM**

- **New task** from the task list and **New lead** from the lead list; a
  party search picker on counterparty, contact and relationship fields; the
  task list defaults to everyone's tasks and the engagement shows every open
  task (#128).
- **A Closed/Signed stage** is appended to every existing sales pipeline
  (`crm.0019`); **AI Chat** is a lead source (#128).
- **Lead numbers never collide** and a number given by the caller is kept
  (#145).
- **An erased customer reads "Erased customer"** in lists and on the
  customer page, which explains the erasure; exports and the API keep the
  stored value (#145).
- **Roles, labels and webhook subscription screens** work for a superuser
  without the staff flag and for staff with no company; label overrides are
  a screen (`core.0019`, #145).

**Dashboard, books and stock**

- **Open Orders means "not shipped yet"** (F-089, #157): shipped, completed,
  cancelled, declined, disputed and partially refunded orders no longer
  count.
- **Close period asks first** (F-091, #159) and confirms with a banner;
  posting into a closed period is refused with the period named.
- **Variant stock follows the warehouses** (F-092, #159): the stock shown
  on the product editor, the storefront and the API is the on-hand sum over
  active warehouses once any warehouse row changes.

**Catalog and SEO**

- **Category and brand pages carry their own SEO copy** (#164): the forms
  show length help and a save warns (never blocks) on placeholders,
  cut-off copy, over-length text and copy duplicated from another row.
- **Variants can override SEO title and meta description** (#165), in a
  new "SEO (override)" section of the variant card; blank inherits the
  product's.

**Sign-in and resilience**

- **The back office keeps working while the cache is down** (F-086,
  #151): pages render, sign-in answers 503 until the cache returns, rate
  limits answer 429. Login throttling is per client address (F-087).
- **A second Company is refused** (`core.E070`, #131): the admin has no
  Add button once one exists and says why; the API answers 409.
- **CSV exports escape formula characters** (#131), so a cell that starts
  with `=`, `+`, `-` or `@` opens as text in a spreadsheet.

## 3. Known limitations

_Written by hand before the tag; the list so far:_

- **One instance per company.** Fincas runs one Company per deployment.
  Staff are not isolated between companies inside one instance, so a second
  Company is refused (`core.E070`, once merged) and another company gets
  its own instance.
- **F-026, F-027, F-028 (cross-company visibility inside one instance):**
  not supported by design, closed as such in `docs/findings-log.md`; they
  re-open at their September severity for any deployment that runs more
  than one Company.
- **Customer detail view scoping:** the customer detail page's tenancy
  scoping fix is parked (uncommitted work, plan decision 11) and is not in
  v0.4.0; with one Company per instance nothing is exposed.
- **Variant stock now follows the warehouses (F-092).** Saving or deleting a
  `WarehouseStock` row sets its variant's `stock` (what the storefront, the
  product editor and the API show) to the on-hand sum over active
  warehouses. A variant whose hand-entered `stock` differs from its
  warehouse rows is corrected the first time any of those rows changes;
  variants with no warehouse rows keep their `stock`. Check the drift before
  upgrading if the storefront's numbers matter.
- **Open Orders on the dashboard means "not shipped yet" (F-089):** shipped,
  completed, cancelled, declined, disputed and partially refunded orders no
  longer count.
- **Journal entry numbers read `JE--00001` (F-095),** a cosmetic double dash;
  fixed in a later release without renumbering existing entries.
- **CRM import behind a transaction-mode pooler (#166):** the import's
  run lock is a Postgres session advisory lock. Through PgBouncer in
  transaction mode or Supabase's Supavisor the unlock can land on another
  backend and the job then reports "being staged by another process" until
  that backend recycles. Point the CRM import (and `migrate`) at the direct
  database host, as `docs/deploy-fly.md` does; a lock that survives pooling
  comes in a later release.
- **Storefront footer contrast in light skins:** the store footer fails
  axe contrast in light skins (hard-coded emerald pill, 60%-opacity text);
  `account.spec.ts` excludes `footer` from its light-skin axe runs.
