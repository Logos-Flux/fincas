## 0. About this release

v0.4.6 lets the assistant (`erp_assist`, the MCP adapter and the staff chat
that uses the same tools) work the middle of an order: find out who an item
is bought from, split an order between a warehouse and one or more vendors,
raise the purchase order for a vendor's part and the pick ticket for the
warehouse's. The back office could already do all of it; the REST API could
not, so this release adds the API too. It is v0.4.5 plus this change:

- **New tools.** `get_default_supplier`, `set_default_supplier`,
  `list_supplier_products`, `update_supplier_product`, `list_shipment_groups`,
  `create_shipment_group`, `update_shipment_group`, `move_order_lines`,
  `create_purchase_order_for_shipment`, `list_pick_tickets`,
  `get_pick_ticket`, `create_pick_ticket` and `update_pick_ticket`.
- **`/api/v1/orders/shipment-groups/`**: the shipments an order is split into
  (list, create, patch, and `move-lines`, which moves order lines into a
  shipment all or none). There is no DELETE. An order's detail lists its
  shipments.
- **`POST /api/v1/fulfillment/pick-tickets/for-shipment/`** finds or creates
  the pick ticket for one shipment, with its lines and bin locations. The
  order editor's "pick ticket" button now uses the same code.
- **`parties/match/` can be part of a service account's contract**, so a
  restricted key can resolve a customer by name, email or phone.
- **Stricter API checks**, listed in section 1.

No migration, no new settings and no new required secrets. The dependency
ranges are those of v0.4.5 (Django 6.0, mcp 1). Install with
`pip install fincas==0.4.6`; the import name stays `golden_erp`.

## 1. Before you upgrade

Upgrading from v0.4.5: install the new version. There is nothing to migrate.
A deployment that runs the MCP adapter as its own process
(`python -m erp_assist.mcp_adapter`) restarts it to get the new tools.

**API requests that are now refused (400).** Each was accepted before and
left records that disagreed with each other:

- moving an order line to another order (`PATCH order-lines/<id>/` with a
  different `order`);
- putting an order line into a shipment of another order, or moving a line
  whose fulfilment has started (it is on a purchase order or pick ticket, or
  has shipped): the rules the order editor already applied;
- a purchase order whose `order`, `shipment_group`, `supplier` or `warehouse`
  belongs to another company than the purchase order.

**Check your service roles before you upgrade.** A `kind="service"` role in
`GOLDEN_ROLES` gains what its existing permissions describe, with no change
to the role:

| The role holds | It gains |
|---|---|
| `orders.view_shipmentgroup` / `add_` / `change_` | reading, creating and editing shipments through the new endpoint |
| `orders.view_shipmentgroup`, `orders.change_orderlineitem`, `orders.view_orderlineitem` | `move-lines` on a shipment |
| `fulfillment.view_pickticket`, `fulfillment.add_pickticket`, `fulfillment.add_pickticketline`, `orders.view_order`, `inventory.view_warehousestock` | `for-shipment` on pick tickets |
| `parties.view_party` and `customers.view_customer` | `parties/match/` (GET and POST; it reads only, inside the account's own company) |

If a role should not gain one of these, remove the permission from it before
upgrading.

**One behavior change in the back office.** A pick ticket made from the
order editor with no warehouse chosen now takes the shipment's own
warehouse, else the first active warehouse **of the order's company**. It
used to take the first active warehouse of any company, which on an instance
with one company is the same warehouse.

From v0.4.4 or earlier, follow the v0.4.5 notes first
([docs/releases/v0.4.5.md](v0.4.5.md) section 1).

## 2. Behavior changes staff will notice

- The chat assistant can say who an item's default vendor is, and record one
  when told. When no vendor, or more than one, is marked as the default it
  says so and asks; it does not choose.
- It can split an order into shipments and move lines between them, raise a
  draft drop-ship purchase order for a shipment and create a pick ticket for
  a warehouse shipment. A purchase order it raises is a **draft**: a person
  reviews and sends it.
- Asking twice does not double up: a second pick ticket request returns the
  first ticket, and a second purchase-order request for the same shipment is
  refused.
- Shipments made through the API or the assistant appear in the order editor
  like any other.

## 3. Known limitations

- **`create_purchase_order_for_shipment` checks for an existing purchase
  order itself**, not on the server: two requests at the same instant could
  still raise two drafts. A purchase order raised some other way for the same
  lines is caught line by line (those lines are left off and named).
- **`set_default_supplier` is several requests**, not one transaction. If it
  is interrupted an item can be left with no default or two;
  `get_default_supplier` reports either state instead of choosing.
- A shipment's `fulfillment_type`, warehouse and supplier can still be
  changed after its pick ticket or purchase order exists. The tools refuse a
  pick ticket for a drop ship and a purchase order for a warehouse shipment;
  the REST endpoints do not.
- A shipment cannot be deleted through the API. One created by a split whose
  lines could not move stays, empty.
- The API covers an order's shipments, not a quote's.
- The limitations in the v0.4.5 notes still apply
  ([docs/releases/v0.4.5.md](v0.4.5.md) section 3).
